# MySQL 高可用架构

> 本文件为「知序学堂」课程知识库资料，供课程 AI 助教检索与问答使用。

## 课程简介

解决数据库单点问题，掌握复制、故障切换、备份恢复与容量规划。

本课程从高可用的目标与指标出发，讲清主从复制原理与复制延迟的成因；随后介绍主流的高可用与集群方案，最后落到备份恢复流程与监控容量规划，形成可运维的数据库架构能力。

## 第一章 高可用基础与复制

本章明确高可用要达成的目标，并打牢主从复制这一基础能力。

### 1.1 高可用的目标与指标

**学习目标**：能正确理解 RTO、RPO 与可用性等级。

**核心知识点**

- RTO 指故障后恢复服务所需时间，RPO 指可容忍丢失的数据量
- 可用性常用几个 9 表示，99.9% 与 99.99% 对应的年停机时间相差十倍
- 高可用方案的选择由业务对 RTO 与 RPO 的要求决定，而不是越复杂越好
- 高可用不仅要防机器故障，还要防人为误操作与机房级故障

**示例**

RPO = 0 通常要求同步复制或强一致共识
RTO = 30 秒通常要求自动故障切换而不是人工介入

**易错点**：只关注机器故障，忽略误删数据这类人为事故，而后者往往造成更长的实际停机。

### 1.2 主从复制原理

**学习目标**：理解 binlog、relay log 与复制线程的协作过程。

**核心知识点**

- 主库把变更写入 binlog，dump 线程把 binlog 发送给从库
- 从库的 IO 线程接收并写入 relay log，SQL 线程再重放 relay log 中的事件
- binlog 有三种格式：STATEMENT 记录语句、ROW 记录行变更、MIXED 混合
- ROW 格式最安全但日志量更大，是当前生产环境的推荐选择

**示例**

```sql
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST='10.0.0.2', SOURCE_USER='repl', SOURCE_PASSWORD='***',
  SOURCE_LOG_FILE='mysql-bin.000003', SOURCE_LOG_POS=154;
START REPLICA;
SHOW REPLICA STATUS\G
```

**易错点**：使用 STATEMENT 格式时，含随机函数或非确定性函数的语句在主从上执行结果可能不一致。

### 1.3 复制延迟与半同步

**学习目标**：能定位复制延迟成因并选择复制模式。

**核心知识点**

- 常见延迟成因：从库单线程重放、大事务、从库配置弱于主库、从库承担大量查询
- 通过 SHOW REPLICA STATUS 中的 Seconds_Behind_Source 观察延迟，但该值在空闲时会失真
- 并行复制可显著缓解单线程重放瓶颈，可按库或按组提交并行
- 半同步复制要求至少一个从库确认收到日志后主库才提交，降低数据丢失风险

**示例**

```sql
SET GLOBAL replica_parallel_workers = 8;
SET GLOBAL replica_parallel_type = 'LOGICAL_CLOCK';
```

**易错点**：写入超大事务会导致从库长时间落后，应把大事务拆分成小批次提交。

## 第二章 故障切换与集群方案

本章对比几种主流高可用方案的能力边界与适用场景。

### 2.1 主从切换与 MHA

**学习目标**：理解自动故障切换的流程与风险点。

**核心知识点**

- 故障切换的核心步骤：探测主库不可用、选出数据最新的从库、提升为新主、其余从库重新指向新主
- 切换过程中需要处理旧主恢复后的数据回补，避免数据分叉
- 自动化切换工具能缩短 RTO，但必须防脑裂，即两个节点同时认为自己是主库
- 切换后应通知应用刷新数据源配置，可用中间件或域名切换来解耦

**示例**

切换判定：连续多次心跳失败、从库延迟小于阈值、多数节点达成共识

**易错点**：网络分区时贸然自动切换可能造成双主写入，必须有仲裁机制防止脑裂。

### 2.2 组复制与 InnoDB Cluster

**学习目标**：理解基于共识协议的强一致复制方案。

**核心知识点**

- 组复制基于 Paxos 类共识协议，多数派确认后才提交，天然避免脑裂与数据分叉
- 单主模式下写入集中在一个节点，多主模式可多节点写入但需处理冲突
- InnoDB Cluster 在组复制之上提供 MySQL Shell 与 Router，简化部署与路由
- 共识方案在多数派不可用时拒绝写入，可用性换一致性，需按业务取舍

**示例**

```bash
var cluster = dba.createCluster('myCluster');
cluster.addInstance('ic@node2:3306');
cluster.status();
```

**易错点**：认为组复制可以无限扩容写入能力，实际上共识开销会随节点增多而上升。

### 2.3 分库分表与中间件

**学习目标**：了解单库性能瓶颈的突破方式与其代价。

**核心知识点**

- 垂直拆分按业务把不同表分到不同库，水平拆分把同一张表按分片键拆到多个库表
- 分片键的选择决定了查询能否命中单库，选错会导致大量跨片查询
- 跨片场景的痛点：分布式事务、跨库 Join、全局唯一 ID、分页排序
- 常见中间件通过路由与结果归并屏蔽分片细节，但会增加运维复杂度

**示例**

订单表按 user_id 取模分成 16 张表：order_0 到 order_15
全局 ID 可用雪花算法生成以避免自增主键冲突

**易错点**：过早分库分表，在数据量尚未到瓶颈时引入复杂度，得不偿失。

## 第三章 备份恢复与运维

本章保证数据可回滚、问题可发现。

### 3.1 备份策略

**学习目标**：能设计全量与增量结合的备份方案。

**核心知识点**

- 逻辑备份用 mysqldump 导出 SQL，体积小但恢复慢；物理备份用 xtrabackup 直接复制数据文件，恢复快
- 全量备份加 binlog 增量可恢复到任意时间点，是常见组合
- 备份必须定期做恢复演练，未验证过的备份等于没有备份
- 备份文件应异地保存并加密，防范机房级故障与数据泄露

**示例**

```bash
mysqldump -uroot -p --single-transaction --master-data=2 tj_course > backup.sql
xtrabackup --backup --target-dir=/data/backup/full
```

**易错点**：mysqldump 未加 --single-transaction，会对表加锁并影响线上业务。

### 3.2 数据恢复流程

**学习目标**：掌握基于备份与 binlog 的时间点恢复方法。

**核心知识点**

- 恢复流程：先还原最近一次全量备份，再用 binlog 重放至目标时间点
- 误删数据时应立即停止写入并备份当前状态，避免覆盖可用数据
- 重放 binlog 时可通过 --start-position 与 --stop-position 精确控制范围
- 恢复完成后要校验数据一致性与业务完整性，而不只是看命令是否成功

**示例**

```bash
mysqlbinlog --start-position=154 --stop-position=892 mysql-bin.000005 | mysql -uroot -p
# 跳过误删语句的 position 区间即可实现时间点恢复
```

**易错点**：发现误删后继续让业务写入，新数据会与待恢复的数据冲突，导致恢复更加困难。

### 3.3 监控与容量规划

**学习目标**：建立数据库的可观测能力与扩容判断标准。

**核心知识点**

- 核心监控指标：QPS、TPS、连接数、活跃会话、慢查询数量、主从延迟、磁盘使用率
- 连接数打满与磁盘写满是最常见的两类突发故障，应设置告警阈值
- 容量规划关注数据增长速率与磁盘余量，预留至少一个扩容周期
- 定期做慢查询治理与索引review，避免性能随数据量增长而持续劣化

**示例**

```sql
SHOW GLOBAL STATUS LIKE 'Threads_connected';
SELECT * FROM information_schema.PROCESSLIST WHERE COMMAND <> 'Sleep';
```

**易错点**：只监控机器指标（CPU、内存）而忽略数据库内部指标，往往等到连接池耗尽才发现问题。

## 综合练习

### 单项选择题

**1. RPO 指的是什么？**

- A. 故障后恢复服务所需的时间
- B. 可容忍丢失的数据量
- C. 每秒查询数
- D. 磁盘使用率

**答案**：B

**解析**：RPO 是恢复点目标，衡量可以容忍丢失多少数据；RTO 是恢复时间目标，衡量停机时长。

**对应知识点**：高可用指标

**2. MySQL 主从复制中，从库负责重放 relay log 的是哪个线程？**

- A. dump 线程
- B. IO 线程
- C. SQL 线程
- D. purge 线程

**答案**：C

**解析**：IO 线程负责把主库 binlog 拉取并写入 relay log，SQL 线程负责重放 relay log 中的事件。

**对应知识点**：复制原理

**3. 下列哪种 binlog 格式记录的是每一行的实际变更，安全性最高？**

- A. STATEMENT
- B. ROW
- C. MIXED
- D. FULL

**答案**：B

**解析**：ROW 格式记录行的实际前后镜像，不依赖语句在主从上的执行结果，因此最安全，代价是日志量更大。

**对应知识点**：binlog 格式

**4. 网络分区时自动故障切换最大的风险是？**

- A. 切换速度太慢
- B. 脑裂导致双主写入
- C. 备份文件损坏
- D. 主从延迟升高

**答案**：B

**解析**：分区时可能出现两个节点都认为自己是主库并同时接受写入，造成数据分叉，必须有仲裁机制防范。

**对应知识点**：故障切换

**5. 使用 mysqldump 备份在线业务库时，为避免长时间锁表应添加哪个参数？**

- A. --lock-all-tables
- B. --single-transaction
- C. --flush-logs
- D. --skip-comments

**答案**：B

**解析**：--single-transaction 在事务隔离快照下导出数据，避免对表加锁，适合 InnoDB 在线备份。

**对应知识点**：备份策略

### 判断题

**1. 备份只要成功执行就算完成，无需定期做恢复演练。**

**答案**：错误

**解析**：错误。未经过恢复验证的备份可能因权限、版本或文件损坏而无法使用，等同于没有备份。

**对应知识点**：备份验证

**2. 发现误删数据后应立即停止写入，并备份当前数据库状态，避免后续数据覆盖可用数据。**

**答案**：正确

**解析**：正确。继续写入会与待恢复数据产生冲突，先止损再恢复是标准处置顺序。

**对应知识点**：恢复流程

**3. 分库分表应在数据量尚小、性能没有问题时就提前实施，以避免将来改造困难。**

**答案**：错误

**解析**：错误。分库分表会引入分布式事务、跨库 Join 等复杂度，应在确实遇到单库瓶颈时再做。

**对应知识点**：分库分表
