# Redis 缓存与分布式锁

> 本文件为「知序学堂」课程知识库资料，供课程 AI 助教检索与问答使用。

## 课程简介

聚焦 Redis 在真实系统中的两大用途：缓存治理与分布式锁。

本课程讲解缓存的使用模式与更新策略，系统分析缓存穿透、击穿、雪崩三类经典问题及应对方案；随后深入分布式锁的实现演进，从 SETNX 到 Redisson 再到 Redlock，并给出热 key、大 key 与多级缓存的治理实践。

## 第一章 缓存基础与使用模式

本章明确为什么要引入缓存，以及缓存与数据库之间如何保持一致。

### 1.1 为什么用缓存

**学习目标**：理解缓存的收益来源与引入后的新问题。

**核心知识点**

- 缓存把磁盘查询转成内存查询，把响应时间从毫秒级降到微秒级
- 缓存能大幅削减数据库 QPS，是抗住高并发的主要手段
- 引入缓存后必须面对一致性、穿透、热点与容量问题
- 不是所有数据都值得缓存，读多写少、可容忍短暂不一致的数据收益最大

**示例**

读流程：先查缓存 → 命中直接返回 → 未命中查数据库 → 回写缓存 → 返回

**易错点**：给写多读少的数据加大缓存，命中率很低，还会带来大量一致性维护成本。

### 1.2 缓存更新策略

**学习目标**：掌握常见的缓存与数据库同步方式及其取舍。

**核心知识点**

- Cache Aside（旁路缓存）最常用：读时未命中回填，写时先更新数据库再删除缓存
- 选择删除缓存而不是更新缓存，可以避免并发写导致的脏数据
- 延迟双删用于缓解主从复制延迟带来的不一致，在写后延时再删一次
- 为缓存设置过期时间是兜底手段，即使出现不一致也能自动恢复

**示例**

写流程：UPDATE db → DEL cache
读流程：GET cache → miss → SELECT db → SET cache EX 300

**易错点**：写成「先删缓存再更新数据库」，并发读会在删除后立刻回填旧值，导致脏数据长期存在，正确顺序是先更新数据库再删缓存。

### 1.3 缓存穿透、击穿、雪崩

**学习目标**：能准确区分三类缓存问题的成因并给出对策。

**核心知识点**

- 穿透：查询本身不存在的数据，缓存和数据库都不命中，请求全部打到数据库，对策是缓存空值或使用布隆过滤器
- 击穿：单个热点 key 过期瞬间大量并发涌入数据库，对策是互斥锁重建或热点数据逻辑过期不物理过期
- 雪崩：大量 key 在同一时间集中过期，或缓存服务整体不可用，对策是过期时间加随机扰动并做多级缓存
- 三者的共同后果都是数据库瞬时压力激增，区别在触发范围与触发方式

**示例**

SET product:9999 "" EX 60        # 缓存空值，防穿透
SET product:1001 value EX 300     # 过期时间加随机值，防雪崩

**易错点**：把穿透和击穿混为一谈：穿透是数据不存在，击穿是热点 key 失效，两者的解决方案完全不同。

## 第二章 分布式锁

本章梳理分布式锁从简单实现到生产可用的演进过程。

### 2.1 SETNX 实现分布式锁

**学习目标**：能写出一个基本可用的分布式锁，并理解其缺陷。

**核心知识点**

- 加锁用 SET key value NX PX 30000，保证原子性与自动过期，避免死锁
- value 必须是唯一标识（如 UUID），释放锁时校验，防止误删他人的锁
- 释放锁需要用 Lua 脚本保证「校验 value + 删除」的原子性
- 业务执行时间超过锁过期时间时，锁会提前释放，导致临界区被并发进入

**示例**

SET lock:order:1001 uuid-abc NX PX 30000
-- 释放：先查 value 是否等于自己的 uuid-abc，是则 DEL，用 Lua 保证原子性

**易错点**：用 SETNX 后再单独 EXPIRE 分两步加锁，如果中间宕机就会留下永不过期的锁，必须用 SET 的 NX PX 一条命令完成。

### 2.2 锁续期与 Redisson

**学习目标**：理解看门狗机制，并能用 Redisson 正确加锁。

**核心知识点**

- 看门狗 Watch Dog 在锁持有期间定期续期，默认每 10 秒把过期时间重置为 30 秒
- 续期只在未显式指定 leaseTime 时生效，一旦手动指定过期时间看门狗就不再工作
- Redisson 基于 Lua 脚本与 PUB/SUB 实现了可重入锁、公平锁、读写锁
- 释放锁时应放在 finally 中，确保异常路径也能解锁

**示例**

```java
RLock lock = redisson.getLock("lock:order:1001");
lock.lock();
try { /* 业务逻辑 */ } finally { lock.unlock(); }
```

**易错点**：调用 lock.lock(10, TimeUnit.SECONDS) 显式指定了过期时间，看门狗不会续期，业务一旦超过 10 秒锁就自动失效。

### 2.3 Redlock 与锁的争议

**学习目标**：了解 Redlock 的设计意图与其局限性。

**核心知识点**

- Redlock 向多个独立 Redis 节点加锁，超过半数成功才算加锁成功，用于降低单点故障风险
- Redlock 依赖各节点时钟大致同步，时钟跳跃会影响安全性
- 对强一致性要求极高的场景，更稳的做法是直接用 ZooKeeper 或 etcd 这类共识系统
- 工程上应优先评估是否真的需要分布式锁，能靠数据库唯一约束或幂等设计解决的就不要引入锁

**示例**

加锁步骤：向 N 个独立节点依次请求加锁 → 多数成功 → 记录总耗时
若总耗时超过锁有效期或成功数不足半数，则向所有节点发起解锁并重试

**易错点**：把 Redlock 当成绝对安全的方案，在时钟不可靠或存在长 GC 停顿的环境下它仍可能失效。

## 第三章 高级缓存实践

本章面向线上真实问题，讲解热 key、大 key 与多级缓存的治理方法。

### 3.1 缓存预热与降级

**学习目标**：掌握系统启动与缓存故障时的应对手段。

**核心知识点**

- 缓存预热在系统上线或大促前主动把热点数据加载进缓存，避免冷启动瞬间压垮数据库
- 缓存降级指在缓存不可用时直接返回兜底数据或静态默认值，保证核心链路可用
- 降级要设置开关并可在监控面板上一键操作，避免临时改代码
- 预热与降级都需要限流配合，否则主动放量仍可能打穿下游

**示例**

启动流程：加载热点商品 id 列表 → 批量 MGET → 未命中的批量查库回填
降级流程：缓存异常 → 开关开启 → 返回兜底值并记录告警

**易错点**：只做降级不做预热，大促零点流量高峰叠加空缓存，数据库仍会被瞬间打满。

### 3.2 热 key 与大 key 治理

**学习目标**：能识别并处理热 key 和大 key 带来的风险。

**核心知识点**

- 热 key 指访问量远超其他 key 的单键，可能把单个 Redis 节点的 CPU 或网络打满
- 热 key 的对策是本地缓存加多副本打散，例如把 key 拆成 key:0 到 key:9 分散到不同节点
- 大 key 指 value 过大（如几 MB 的 Hash、上万元素的 List），会阻塞单线程、拖慢网络传输
- 大 key 的治理思路是拆分、压缩、改用更合适的数据结构，并避免使用 HGETALL、KEYS 等命令

**示例**

```bash
redis-cli --bigkeys            # 扫描大 key
redis-cli --hotkeys            # 需开启 LFU 淘汰策略
redis-cli --latency            # 观察延迟抖动
```

**易错点**：在生产环境直接执行 KEYS *，会阻塞 Redis 单线程直到扫描完成，应改用 SCAN 渐进遍历。

### 3.3 多级缓存架构

**学习目标**：理解多级缓存的层次划分与一致性问题。

**核心知识点**

- 典型层次：本地缓存（Caffeine）→ Redis 分布式缓存 → 数据库
- 本地缓存速度最快但有容量上限，且多实例之间难以保持一致
- 通过消息广播或短过期时间来解决本地缓存的失效同步问题
- 多级缓存能显著降低 Redis 与数据库压力，是应对超大流量的常见架构

**示例**

查询顺序：Caffeine 命中 → 返回
          未命中 → Redis 命中 → 回填本地并返回
          仍未命中 → 查库 → 回填 Redis 与本地 → 返回

**易错点**：给本地缓存设置过长的过期时间，会导致数据更新后部分实例长时间返回旧值。

## 综合练习

### 单项选择题

**1. 查询一个数据库中根本不存在的数据，导致请求每次都绕过缓存直接打数据库，这属于？**

- A. 缓存穿透
- B. 缓存击穿
- C. 缓存雪崩
- D. 缓存预热

**答案**：A

**解析**：数据本身不存在，缓存与数据库都无法命中，请求全部落到数据库，这是缓存穿透的典型特征。

**对应知识点**：缓存穿透

**2. 大量缓存 key 在同一时刻集中过期，导致数据库瞬时压力激增，这属于？**

- A. 缓存穿透
- B. 缓存击穿
- C. 缓存雪崩
- D. 缓存降级

**答案**：C

**解析**：大量 key 同时失效是缓存雪崩的典型成因，对策是给过期时间加随机扰动并做多级缓存。

**对应知识点**：缓存雪崩

**3. 用 Redis 实现分布式锁时，正确的加锁命令是？**

- A. SETNX lock 1 之后再单独执行 EXPIRE
- B. SET lock uuid NX PX 30000
- C. LPUSH lock uuid
- D. HSET lock uuid 1

**答案**：B

**解析**：SET 配合 NX PX 能在一条原子命令中完成「不存在才设置」与「设置过期时间」，避免分两步加锁时宕机留下死锁。

**对应知识点**：分布式锁实现

**4. Redisson 的看门狗机制在什么情况下不会生效？**

- A. 使用 lock.lock() 无参调用时
- B. 显式指定了 leaseTime 时
- C. 使用可重入锁时
- D. 使用公平锁时

**答案**：B

**解析**：一旦手动指定了过期时间 leaseTime，看门狗就不再自动续期，业务执行超时后锁会提前释放。

**对应知识点**：看门狗机制

**5. 缓存与数据库的更新顺序，推荐的做法是？**

- A. 先删除缓存，再更新数据库
- B. 先更新数据库，再删除缓存
- C. 先更新缓存，再更新数据库
- D. 先更新数据库，再更新缓存

**答案**：B

**解析**：先更新数据库再删除缓存，可以避免并发读在删除后立刻把旧值回填，是 Cache Aside 的推荐顺序。

**对应知识点**：缓存更新策略

### 判断题

**1. 释放分布式锁时需要用唯一标识校验持有者，防止误删其他实例的锁。**

**答案**：正确

**解析**：正确。若业务执行超时导致锁自动过期，别的实例可能已经拿到锁，此时直接 DEL 会误删他人的锁。

**对应知识点**：锁安全性

**2. 在生产环境使用 KEYS * 查询所有键是安全的，因为它只是读操作。**

**答案**：错误

**解析**：错误。Redis 是单线程处理命令，KEYS * 会遍历全部键并阻塞直到完成，应改用 SCAN 渐进式遍历。

**对应知识点**：大 key 与危险命令

**3. 为防止缓存雪崩，可以给同类数据的过期时间加上随机偏移量。**

**答案**：正确

**解析**：正确。随机化过期时间能避免大量 key 在同一秒集中失效，是最简单有效的雪崩预防手段。

**对应知识点**：雪崩预防
