# Redis 集群与高并发

> 本文件为「知序学堂」课程知识库资料，供课程 AI 助教检索与问答使用。

## 课程简介

从持久化、主从到 Cluster，系统性解决 Redis 的可靠性与扩展性问题。

本课程讲解 RDB 与 AOF 持久化及内存淘汰策略，深入主从复制与哨兵故障转移机制，最后展开 Redis Cluster 的分片、伸缩与高并发场景下的实践要点。

---

## 第一章 持久化与内存管理

本章解决「宕机后数据还在吗」与「内存满了怎么办」两个问题。

### 1.1 RDB 与 AOF

**学习目标**：掌握两种持久化方式的特点与配置方式。

**核心知识点**

- RDB 是某一时刻的数据快照，文件紧凑、恢复快，但两次快照之间的数据可能丢失
- AOF 记录写命令，数据安全性更高，但文件更大、恢复更慢
- AOF 刷盘策略 always 最安全但性能最差，everysec 在安全与性能之间取得平衡
- AOF 文件会随写入增长，需要通过重写压缩体积

**示例**

```conf
save 900 1
save 300 10
appendonly yes
appendfsync everysec
BGREWRITEAOF
```

**易错点**：只使用 RDB 且快照间隔较长，宕机时会丢失间隔内全部写入，对数据敏感的业务应开启 AOF。

### 1.2 混合持久化与选择

**学习目标**：能根据业务对数据丢失的容忍度选择持久化方案。

**核心知识点**

- 混合持久化在 AOF 重写时以 RDB 格式写入头部，兼顾恢复速度与数据安全
- 纯缓存场景可只用 RDB 甚至关闭持久化，以换取更高性能
- 持久化不是备份，仍需额外做备份与异地保存
- fork 子进程做持久化时会短暂阻塞，内存越大阻塞越明显

**示例**

```conf
aof-use-rdb-preamble yes   # 开启混合持久化
```

**易错点**：在内存巨大的实例上频繁触发 fork，会造成明显的主线程停顿与内存瞬时翻倍风险。

### 1.3 内存淘汰策略

**学习目标**：掌握八种淘汰策略的含义与选择依据。

**核心知识点**

- noeviction 在内存满时直接报错，适合作数据存储而非缓存的场景
- allkeys-lru 与 allkeys-lfu 对所有键做淘汰，是纯缓存场景的常用选择
- volatile-* 系列只淘汰设置了过期时间的键，需谨慎使用否则可能提前丢失数据
- maxmemory 必须显式设置，否则 Redis 会一直占用内存直至被系统杀死

**示例**

```conf
maxmemory 4gb
maxmemory-policy allkeys-lru
```

**易错点**：使用 volatile-lru 但大量键没有设置过期时间，内存满时会因无可淘汰键而直接写入失败。

## 第二章 主从复制与哨兵

本章解决读扩展与单点故障问题。

### 2.1 主从复制

**学习目标**：理解全量同步与增量同步的触发条件。

**核心知识点**

- 首次连接触发全量同步：主库生成 RDB 发给从库，并把期间的新命令缓存后补发
- 增量同步基于 repl_backlog 环形缓冲区，从库上报偏移量后主库只补发缺失部分
- repl_backlog_size 过小会导致从库短暂断连后就退化为全量同步，造成主库压力激增
- 从库默认只读，可通过 replica-read-only 调整，但生产环境不建议放开

**示例**

```conf
replicaof 10.0.0.2 6379
repl-backlog-size 64mb
```

**易错点**：复制缓冲区过小，从库网络抖动后就触发全量同步，主库会因生成 RDB 而明显卡顿。

### 2.2 哨兵机制与故障转移

**学习目标**：理解哨兵的监控、通知、自动故障转移三个职责。

**核心知识点**

- 哨兵持续监控主从节点，主观下线后需多个哨兵达成共识才判定客观下线
- 故障转移流程：选出领导者哨兵、从从库中选新主、切换其余从库、通知客户端
- 新主选择依据：优先级、复制偏移量、运行 id
- 哨兵自身也需部署奇数个节点，避免出现平票无法达成共识

**示例**

```conf
sentinel monitor mymaster 10.0.0.2 6379 2
sentinel down-after-milliseconds mymaster 30000
sentinel failover-timeout mymaster 180000
```

**易错点**：哨兵数量为偶数且在网络分区时，可能出现无法达成多数派而反复切换或无法切换的情况。

### 2.3 复制风暴与优化

**学习目标**：避免复制过程拖垮主库。

**核心知识点**

- 复制风暴指大量从库同时向主库发起全量同步，导致主库频繁 fork 与带宽占满
- 缓解手段：错开重启时间、使用树形复制由从库再向下游复制、适当增大 repl_backlog
- 从库执行 BGSAVE 与重写 AOF 也会消耗资源，应避免与主库备份同时进行
- 读写分离时要注意主从延迟，刚写入就读的强一致场景应走主库

**示例**

错峰重启：按分片或机房分批重启从库
树形复制：主库 → 中间层从库 → 边缘从库

**易错点**：写入后立刻从从库读取，在主从延迟下会读不到刚写入的数据，出现「写了却查不到」的现象。

## 第三章 Cluster 与高并发实践

本章解决单机内存与吞吐上限问题。

### 3.1 分片与槽位

**学习目标**：理解哈希槽的分片机制与多键操作限制。

**核心知识点**

- Redis Cluster 把键空间划分为 16384 个哈希槽，槽位分配到各主节点
- 键的槽位由 CRC16(key) 对 16384 取模得到
- 多键命令要求所有键在同一槽位，可用 hash tag 把相关键强制落到同一槽
- 客户端通过 MOVED 重定向感知槽位归属，集群拓扑可自动更新

**示例**

SET user:{1001}:name "张三"
SET user:{1001}:age 20
# 使用 hash tag，两个键保证落在同一个槽

**易错点**：跨槽执行 MGET 或事务会直接报错，需要提前用 hash tag 设计好键的布局。

### 3.2 集群伸缩与迁移

**学习目标**：掌握扩缩容的操作流程与注意事项。

**核心知识点**

- 扩容：加入新节点 → 分配槽位 → 迁移槽内数据 → 通知集群拓扑变更
- 缩容：先迁移出待下线节点的槽位，确认无数据后再移除节点
- 迁移过程中客户端可能收到 ASK 重定向，这是正常的过渡状态
- 集群要求至少 3 个主节点，并建议每个主节点配一个从节点以支持故障转移

**示例**

```bash
redis-cli --cluster add-node 10.0.0.9:6379 10.0.0.2:6379
redis-cli --cluster reshard 10.0.0.2:6379
redis-cli --cluster check 10.0.0.2:6379
```

**易错点**：迁移槽位时使用过大的批量参数，会长时间阻塞槽位访问，影响线上请求。

### 3.3 高并发实践要点

**学习目标**：掌握高并发场景下的关键取舍。

**核心知识点**

- Redis 命令处理是单线程的，任何慢命令都会阻塞后续所有请求
- 禁止在生产使用 KEYS、FLUSHALL 等阻塞命令，用 SCAN 分批遍历替代
- 用 Pipeline 批量发送减少网络往返，但单次批量不宜过大以免阻塞
- 热点键可通过多副本打散或本地缓存分担，避免单节点被打满

**示例**

```bash
redis-cli --intrinsic-latency 100     # 检测固有延迟
redis-cli --latency-history           # 观察延迟历史变化
SLOWLOG GET 10                        # 查看慢命令
```

**易错点**：把 Redis 当关系库使用，执行复杂的聚合计算，长耗时会阻塞整个实例。

## 综合练习

### 单项选择题

**1. 关于 RDB 与 AOF 的对比，下列说法正确的是？**

- A. RDB 文件大、恢复慢
- B. AOF 记录写命令，数据安全性更高
- C. AOF 不需要重写
- D. RDB 无法用于备份

**答案**：B

**解析**：AOF 记录写命令，可按策略刷盘，数据安全性更高，代价是文件更大、恢复更慢，需要重写压缩。

**对应知识点**：持久化

**2. 纯缓存场景下，常用的内存淘汰策略是？**

- A. noeviction
- B. volatile-ttl
- C. allkeys-lru
- D. allkeys-random 以外的策略均不可用

**答案**：C

**解析**：allkeys-lru 对所有键按最近最少使用淘汰，是纯缓存场景的常用选择；noeviction 会在内存满时直接报错。

**对应知识点**：内存淘汰

**3. Redis Cluster 中键空间的哈希槽总数是？**

- A. 1024
- B. 4096
- C. 16384
- D. 65536

**答案**：C

**解析**：Redis Cluster 将键空间划分为 16384 个哈希槽，键通过 CRC16 取模映射到具体槽位。

**对应知识点**：集群分片

**4. 要让多个键保证落在同一个哈希槽，应使用什么机制？**

- A. Pipeline
- B. 事务
- C. hash tag（花括号）
- D. Lua 脚本

**答案**：C

**解析**：在键中使用花括号包裹的 hash tag，Redis 只对花括号内内容计算槽位，从而保证相关键落在同一槽。

**对应知识点**：多键操作

**5. 哨兵部署为奇数个节点的主要原因是？**

- A. 节省机器资源
- B. 避免投票平票导致无法达成共识
- C. 提高读写性能
- D. 减少网络流量

**答案**：B

**解析**：哨兵需要多数派达成共识才能判定客观下线并执行故障转移，奇数节点可避免平票僵局。

**对应知识点**：哨兵机制

### 判断题

**1. repl_backlog_size 设置过小，会导致从库短暂断连后退化为全量同步，加重主库压力。**

**答案**：正确

**解析**：正确。环形缓冲区不足时无法补发缺失的增量数据，从库只能重新做全量同步。

**对应知识点**：主从复制

**2. 在生产环境使用 KEYS 命令遍历所有键是安全的，因为它是只读操作。**

**答案**：错误

**解析**：错误。Redis 单线程处理命令，KEYS 会遍历全部键并阻塞其他请求，应改用 SCAN 分批遍历。

**对应知识点**：高并发实践

**3. 开启读写分离后，刚写入主库的数据立即从从库读取，一定能够读到。**

**答案**：错误

**解析**：错误。主从复制存在延迟，刚写入的数据可能尚未同步到从库，强一致读应走主库。

**对应知识点**：读写分离
