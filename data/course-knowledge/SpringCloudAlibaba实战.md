# Spring Cloud Alibaba 实战

> 本文件为「知序学堂」课程知识库资料，供课程 AI 助教检索与问答使用。

## 课程简介

用 Nacos、Sentinel、Seata 构建一套可落地的微服务治理体系。

本课程从 Alibaba 微服务生态与组件选型讲起，深入 Nacos 的注册与配置能力；随后讲解 Sentinel 的流控、熔断与热点参数规则，最后覆盖 Seata 分布式事务与事务消息，形成完整的微服务治理落地方案。

---

## 第一章 组件概览与 Nacos

本章介绍生态构成，并把 Nacos 的注册与配置两项能力讲透。

### 1.1 生态与组件选型

**学习目标**：建立对 Alibaba 微服务组件体系的整体认识。

**核心知识点**

- Nacos 兼具注册中心与配置中心双重角色，可减少一个中间件的运维成本
- Sentinel 负责流量控制、熔断降级与系统保护，提供控制台可视化规则配置
- Seata 解决分布式事务问题，RocketMQ 承担消息与事务消息能力
- 组件选型应基于团队能力与运维成本，而不是组件数量

**示例**

典型组合：Nacos（注册+配置） + Sentinel（流控） + Seata（事务） + RocketMQ（消息）

**易错点**：把 Nacos 既当注册中心又当配置中心却不做集群与持久化，单点故障会同时影响服务发现与配置下发。

### 1.2 Nacos 注册中心

**学习目标**：掌握服务注册、健康检查与实例管理。

**核心知识点**

- 临时实例通过心跳保活，心跳超时后被自动剔除，对应 AP 模式
- 持久实例由服务端主动探测健康状态，即使心跳中断也不会被立即剔除，对应 CP 模式
- 可通过权重设置调整流量分配，用于灰度或按机器性能分流
- 保护阈值用于在健康实例比例过低时防止流量全部被摘除

**示例**

```yaml
spring:
  cloud:
    nacos:
      discovery:
        server-addr: 127.0.0.1:8848
        namespace: dev
        group: DEFAULT_GROUP
```

**易错点**：开发环境与生产环境共用同一个命名空间，测试实例会被生产调用方发现并误调用。

### 1.3 Nacos 配置中心

**学习目标**：掌握配置的隔离、推送与回滚。

**核心知识点**

- 通过命名空间、分组、dataId 三级维度组织配置，实现环境与业务隔离
- 配置变更后 Nacos 通过长轮询推送通知客户端拉取最新配置
- Nacos 保留历史版本，支持一键回滚到任意历史配置
- 公共配置可通过 shared-configs 与 extension-configs 被多个服务复用

**示例**

```yaml
spring:
  cloud:
    nacos:
      config:
        server-addr: 127.0.0.1:8848
        shared-configs:
          - data-id: common.yaml
            refresh: true
```

**易错点**：把数据库密码写成明文并允许所有应用读取，凭据一旦泄露影响面极大，应加密并收敛权限。

## 第二章 流量治理

本章用 Sentinel 解决流量突增与下游故障两类问题。

### 2.1 Sentinel 流控

**学习目标**：掌握流控规则的维度与效果。

**核心知识点**

- 流控基于 QPS 或线程数两个维度，线程数维度可反映实际并发占用
- 流控模式：直接、关联、链路，用于处理资源之间的相互影响
- 流控效果：快速失败、预热（Warm Up）、排队等待
- 冷启动预热适合刚启动的服务，避免瞬间被打满

**示例**

资源：GET:/courses/{id}
阈值类型：QPS
单机阈值：100
流控效果：Warm Up，预热时长 10s

**易错点**：只设置单机阈值而不做集群限流，扩容后集群总放行量会随之翻倍。

### 2.2 熔断降级规则

**学习目标**：掌握三种熔断策略的适用场景。

**核心知识点**

- 慢调用比例：当响应时间超过阈值的请求占比过高时熔断，适合接口变慢的场景
- 异常比例：当异常请求占比超过阈值时熔断，适合下游整体故障的场景
- 异常数：按单位时间内的异常数量触发，适合流量较小的接口
- 熔断时长结束后进入半开状态，放行少量请求试探是否恢复

**示例**

策略：慢调用比例
最大 RT：500ms
比例阈值：0.5
熔断时长：10s
最小请求数：10

**易错点**：最小请求数设置过小，在低流量时段会被偶发的一两个异常触发熔断，产生误伤。

### 2.3 热点参数与系统规则

**学习目标**：掌握热点参数限流与系统自适应保护。

**核心知识点**

- 热点参数规则可针对方法中的特定参数值限流，例如按商品 ID 限制单个热销商品
- 可对参数值设置例外项，允许特定值不参与限流
- 系统规则从入口流量、CPU 使用率、平均 RT、并发线程数等维度做整体保护
- 系统规则是兜底手段，不能替代针对具体接口的业务限流

**示例**

```java
@SentinelResource(value = "queryGoods", blockHandler = "handleBlock")
public Goods queryGoods(Long goodsId, String type) { }
```

**易错点**：把 blockHandler 与 fallback 混淆：前者处理限流与熔断，后者处理业务异常，签名要求也不同。

## 第三章 分布式事务与消息

本章解决跨服务数据一致性问题。

### 3.1 Seata 分布式事务

**学习目标**：理解 Seata 的角色划分与模式差异。

**核心知识点**

- 三个角色：TC 事务协调者、TM 事务管理者、RM 资源管理者
- AT 模式通过解析 SQL 生成前后镜像实现自动回滚，对业务侵入小
- TCC 模式由业务自行实现 Try、Confirm、Cancel 三个阶段，控制力更强但成本更高
- SAGA 模式适合长流程业务，通过补偿操作回滚已完成的步骤

**示例**

```java
@GlobalTransactional
public void createOrder(OrderDTO dto) {
    orderService.create(dto);
    stockService.deduct(dto.getGoodsId(), dto.getCount());
}
```

**易错点**：误以为加了全局事务注解就万事大吉，AT 模式仍要求业务 SQL 可被正确解析且表有主键。

### 3.2 RocketMQ 事务消息

**学习目标**：理解事务消息与最终一致性方案。

**核心知识点**

- 事务消息流程：发送半消息 → 执行本地事务 → 提交或回滚半消息 → 消费者消费
- 若生产者未及时回查，Broker 会主动回查本地事务状态以决定消息投递
- 消息消费需保证幂等，通过唯一业务键去重防止重复处理
- 事务消息用于解决「本地事务与消息发送」的原子性，而不是替代分布式事务

**示例**

本地事务成功 → 提交半消息
本地事务失败 → 回滚半消息，消息不会被投递

**易错点**：消费者未做幂等处理，消息重投时会造成重复扣款或重复发货。

### 3.3 最终一致性实践

**学习目标**：掌握以最终一致性替代强一致的工程思路。

**核心知识点**

- 大多数业务并不需要强一致，可用最终一致降低复杂度与耦合
- 常见手段：本地消息表、事务消息、定时对账补偿
- 补偿逻辑必须幂等且可重试，否则补偿本身会成为新的故障源
- 对账任务是最后一道防线，用于发现并修复长期不一致的数据

**示例**

本地消息表：业务与消息写入同一本地事务 → 定时任务扫描待发送消息 → 投递成功后更新状态

**易错点**：补偿逻辑不具备幂等性，重试多次后把数据改得更乱，反而放大损失。

## 综合练习

### 单项选择题

**1. Nacos 中临时实例采用的是一致性模型是？**

- A. CP
- B. AP
- C. BASE 以外的模型
- D. 强一致

**答案**：B

**解析**：临时实例通过心跳保活、超时剔除，优先保证可用性，属于 AP 模型；持久实例才走 CP。

**对应知识点**：Nacos 注册中心

**2. Sentinel 中适合「服务刚启动、需要缓慢放量」的流控效果是？**

- A. 快速失败
- B. Warm Up 预热
- C. 排队等待
- D. 链路模式

**答案**：B

**解析**：Warm Up 会在预热时长内逐步把放行阈值提升到设定值，避免刚启动的服务被瞬间打满。

**对应知识点**：流控效果

**3. 对某个热销商品单独限制访问量的 Sentinel 能力是？**

- A. 系统规则
- B. 热点参数规则
- C. 链路规则
- D. 授权规则

**答案**：B

**解析**：热点参数规则可针对方法中特定参数值单独限流，适合按商品 ID、用户 ID 做精细化控制。

**对应知识点**：热点参数

**4. Seata 中负责事务协调的角色是？**

- A. TM
- B. RM
- C. TC
- D. TC 与 RM 合并

**答案**：C

**解析**：TC 是事务协调者，负责维护全局事务状态；TM 负责发起与结束全局事务，RM 管理分支资源。

**对应知识点**：Seata 角色

**5. RocketMQ 事务消息中，若生产者执行本地事务后未及时告知结果，Broker 会如何处理？**

- A. 直接丢弃消息
- B. 主动回查生产者的事务状态
- C. 投递空消息
- D. 转发给其他生产者

**答案**：B

**解析**：Broker 会主动回查生产者的本地事务状态，据此决定提交还是回滚半消息。

**对应知识点**：事务消息

### 判断题

**1. Sentinel 的最小请求数设置过小，可能在低流量时段被偶发异常误触发熔断。**

**答案**：正确

**解析**：正确。最小请求数是触发熔断统计的门槛，设置过小会让个位数的异常就满足比例条件。

**对应知识点**：熔断规则

**2. @SentinelResource 的 blockHandler 与 fallback 作用相同，可以互相替换。**

**答案**：错误

**解析**：错误。blockHandler 处理限流、熔断等 BlockException，fallback 处理业务异常，两者签名要求也不同。

**对应知识点**：Sentinel 注解

**3. 使用事务消息后，消费者无需考虑幂等，消息只会被消费一次。**

**答案**：错误

**解析**：错误。消息中间件通常提供至少一次投递，消费者必须自己做幂等，否则重投会造成重复处理。

**对应知识点**：消息幂等
