# Java 微服务实战入门

> 本文件为「知序学堂」课程知识库资料，供课程 AI 助教检索与问答使用。

## 课程简介

从单体走向微服务，完整认识服务拆分、通信、治理与部署。

本课程先建立微服务的架构认知与服务拆分原则，再讲解注册发现、声明式调用与配置中心，最后覆盖网关、容错、链路追踪与容器化部署，形成微服务落地的完整视图。

---

## 第一章 微服务架构认知

本章讲清为什么要拆、怎么拆，以及整体技术栈的构成。

### 1.1 从单体到微服务

**学习目标**：理解单体架构的痛点与微服务的收益代价。

**核心知识点**

- 单体应用的问题：代码耦合、构建变慢、难以按模块独立扩容、一处故障影响全局
- 微服务的收益：独立开发部署、按需扩容、技术异构、故障隔离
- 微服务的代价：分布式复杂度、运维成本、数据一致性、链路排查难度上升
- 微服务不是银弹，团队规模小、业务尚未稳定时单体往往更合适

**示例**

单体：一个 war 包包含用户、课程、订单全部模块
微服务：user-service、course-service、order-service 独立部署与扩容

**易错点**：为了追求架构先进性而拆分过细，导致服务数量爆炸、一次需求要改十几个仓库。

### 1.2 服务拆分原则

**学习目标**：掌握按业务能力与领域边界拆分的方法。

**核心知识点**

- 优先按业务能力拆分，例如用户、课程、订单、支付各成一个服务
- 强调高内聚低耦合，把经常一起变化的逻辑放在同一个服务内
- 避免分布式单体：服务虽然拆开了，但每次发布仍必须同时上线
- 数据库应避免跨服务直连，服务间通过接口交互，各自管理自己的数据

**示例**

合理拆分：订单服务负责订单生命周期，用户服务负责账号与权限
不合理拆分：把订单的查询与写入拆成两个服务，导致二者强耦合

**易错点**：多个服务直连同一张表，表结构一改就牵动多个服务，等于没有拆分。

### 1.3 技术栈全景

**学习目标**：建立对微服务各组件的整体认识。

**核心知识点**

- 基础组件：注册中心、配置中心、网关、服务调用、负载均衡
- 治理组件：熔断限流、链路追踪、日志聚合、监控告警
- 数据组件：分布式事务、消息队列、分布式缓存与分布式锁
- 部署组件：容器化、编排、CI/CD 流水线

**示例**

典型组合：Nacos + Spring Cloud Gateway + OpenFeign + Sentinel + SkyWalking

**易错点**：一次性引入全部组件，团队尚未掌握就上生产，反而制造出更多故障点。

## 第二章 服务通信与注册发现

本章解决服务之间如何找到彼此并稳定调用的问题。

### 2.1 服务注册与发现

**学习目标**：理解注册中心的工作机制。

**核心知识点**

- 服务启动时把自身地址注册到注册中心，并定期发送心跳表示存活
- 调用方从注册中心获取实例列表，本地缓存并感知变更
- 注册中心需具备高可用，通常部署为集群并保证数据一致
- 实例下线有主动注销与心跳超时剔除两种方式

**示例**

```yaml
spring:
  cloud:
    nacos:
      discovery:
        server-addr: 127.0.0.1:8848
```

**易错点**：注册中心单点部署，一旦不可用会导致新实例无法上线、调用方无法更新实例列表。

### 2.2 声明式调用 OpenFeign

**学习目标**：会用接口的方式发起远程调用。

**核心知识点**

- Feign 通过接口加注解声明远程调用，底层仍是 HTTP，屏蔽了手工拼装请求的过程
- 需在启动类开启 @EnableFeignClients，接口用 @FeignClient 指定服务名
- 集成负载均衡后可自动在多个实例间轮询或按权重选择
- 必须显式配置连接超时与读超时，否则默认值可能不适合业务

**示例**

```java
@FeignClient(name = "course-service")
public interface CourseClient {
    @GetMapping("/courses/{id}")
    CourseVO getCourse(@PathVariable("id") Long id);
}
```

**易错点**：Feign 接口的 @PathVariable 不写 value 在某些版本下会导致参数绑定失败，应显式指定名称。

### 2.3 配置中心

**学习目标**：理解配置集中管理与动态刷新的价值。

**核心知识点**

- 配置中心统一管理多环境配置，避免配置散落在各服务的配置文件里
- 支持按命名空间与分组隔离环境与业务，防止测试配置污染生产
- 配置变更后可推送通知服务动态刷新，无需重启应用
- 敏感配置需要加密存储与权限控制，避免凭据泄露

**示例**

```yaml
spring:
  config:
    import: nacos:tj-course-dev.yaml
  cloud:
    nacos:
      config:
        server-addr: 127.0.0.1:8848
```

**易错点**：把数据库密码明文放在配置中心且不限制读取权限，任何能访问配置中心的人都能拿到凭据。

## 第三章 服务治理与部署

本章补齐稳定性保障与上线能力。

### 3.1 网关与统一入口

**学习目标**：理解网关在微服务中的定位。

**核心知识点**

- 网关是外部流量唯一入口，负责路由转发、鉴权、限流与日志
- 下游服务信任网关注入的用户信息头，避免每个服务重复解析令牌
- 网关通过服务名转发，服务实例增减对客户端透明
- 网关层只处理横切关注点，不写业务逻辑

**示例**

```yaml
server:
  port: 10010
spring:
  cloud:
    gateway:
      routes:
        - id: course
          uri: lb://course-service
          predicates:
            - Path=/cs/**
```

**易错点**：把大量业务校验放在网关，导致网关成为难以测试与发布的巨型模块。

### 3.2 容错与链路追踪

**学习目标**：掌握稳定性保障与问题定位手段。

**核心知识点**

- 超时、限流、熔断、降级是四类基本容错手段，超时是最基础的保障
- 熔断在下游持续失败时快速失败，避免线程资源被耗尽
- 链路追踪为每次请求分配 TraceId 并沿调用链透传，是分布式排查的前提
- 把 TraceId 输出到日志，才能把一次请求的全部日志串起来

**示例**

Feign 集成熔断后可为每个远程调用指定 fallback
日志格式中加入 traceId 占位符以便检索

**易错点**：只做了熔断但没有配置降级兜底，熔断打开后用户只能看到报错页面。

### 3.3 容器化部署

**学习目标**：理解微服务的交付与运行方式。

**核心知识点**

- 容器镜像把应用与运行环境一同打包，保证各环境行为一致
- 镜像应分层构建并只复制必要产物，减小体积、加快拉取
- 容器需要设置合理的内存与 CPU 限制，并让 JVM 感知容器限额
- 健康检查配合滚动更新，可实现不停机发布

**示例**

```dockerfile
FROM eclipse-temurin:17-jre
WORKDIR /app
COPY target/app.jar app.jar
ENTRYPOINT ["java","-jar","/app/app.jar"]
```

**易错点**：在容器中未配置 JVM 堆上限，JVM 可能按宿主机内存计算堆大小，最终被容器 OOM 杀死。

## 综合练习

### 单项选择题

**1. 关于微服务的代价，下列说法正确的是？**

- A. 微服务没有额外成本，越早拆越好
- B. 引入分布式复杂度、运维成本与数据一致性挑战
- C. 拆分后不再需要监控
- D. 拆分后单个服务无需考虑性能

**答案**：B

**解析**：微服务带来独立部署与扩容等收益，同时引入分布式复杂度、运维成本与一致性难题，需权衡取舍。

**对应知识点**：微服务认知

**2. 以下哪种情况最符合「合理拆分」？**

- A. 把订单的查询与写入拆成两个服务
- B. 多个服务直连同一张数据库表
- C. 按业务能力划分用户、课程、订单服务
- D. 每次发布必须同时上线所有服务

**答案**：C

**解析**：按业务能力拆分并保持高内聚低耦合是合理做法；直连同一张表和必须同时上线都属于分布式单体。

**对应知识点**：服务拆分

**3. 使用 OpenFeign 声明远程调用时，需要在启动类添加哪个注解？**

- A. @EnableFeignClients
- B. @EnableDiscoveryClient
- C. @EnableCircuitBreaker
- D. @EnableAsync

**答案**：A

**解析**：@EnableFeignClients 用于开启 Feign 客户端扫描，@FeignClient 接口才会被生成代理实现。

**对应知识点**：服务调用

**4. 微服务中调用方如何感知服务实例的增减？**

- A. 通过手工修改配置文件
- B. 通过注册中心的实例列表与变更通知
- C. 通过数据库表记录
- D. 通过重启应用读取最新地址

**答案**：B

**解析**：注册中心维护实例列表并在变更时通知客户端，调用方据此更新本地缓存，无需人工干预。

**对应知识点**：注册发现

**5. 关于链路追踪中的 TraceId，正确的做法是？**

- A. 只在网关生成但不必透传
- B. 为每次请求生成并沿调用链透传，同时输出到日志
- C. 每个服务各自生成独立 ID
- D. 仅在出错时生成

**答案**：B

**解析**：TraceId 必须沿调用链透传并写入日志，才能把一次请求跨多个服务的日志串联起来。

**对应知识点**：链路追踪

### 判断题

**1. 多个微服务直连同一张数据库表，是合理的拆分方式。**

**答案**：错误

**解析**：错误。直连同一张表会让表结构变更牵动多个服务，形成隐形耦合，违背服务自治原则。

**对应知识点**：数据边界

**2. 远程调用必须显式设置超时时间，否则线程可能被长时间占用。**

**答案**：正确

**解析**：正确。超时是最基础的容错手段，缺省无限等待会快速耗尽调用方的线程资源。

**对应知识点**：容错

**3. 容器中运行 JVM 时无需设置堆上限，JVM 会正确识别容器内存限制。**

**答案**：错误

**解析**：错误。JVM 在旧版本或未开启容器感知时会按宿主机内存计算堆大小，容易超出容器限额被 OOM 杀死。

**对应知识点**：容器化部署
